# generate_go_project.py — Go + gRPC Service Generator

A small Python tool that scaffolds a complete Go gRPC service with PostgreSQL. You answer two questions (project name and database name) and it generates a fully wired project: config, repository, service, handler, proto definition, and `main.go`.

## What it does

Every time you start a new gRPC service you normally have to create the same files and connect them by hand. This tool removes that work:

- Prompts for the **project name** (Go module path) and the **database name**.
- Creates the full directory tree and all source files.
- Replaces the project and database names inside every generated file.
- Runs `go mod init`, `protoc`, and `go mod tidy` if the tools are installed.

The result is a service that compiles and runs as soon as PostgreSQL is available.

## Requirements

| Tool | Needed for | Required |
|------|-----------|----------|
| Python 3.9+ | Running the generator | Yes |
| Go 1.21+ | `go mod init`, `go mod tidy`, running the service | Recommended |
| `protoc` | Generating Go code from `.proto` | Recommended |
| `protoc-gen-go` | protoc plugin for messages | Recommended |
| `protoc-gen-go-grpc` | protoc plugin for gRPC stubs | Recommended |
| PostgreSQL | Running the generated service | At runtime |

The generator itself uses only the Python standard library. If Go or protoc are missing, it still creates all files and prints the commands you need to run manually.

Install the protoc plugins:

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
```

Make sure `$(go env GOPATH)/bin` is on your `PATH`.

## Usage

```bash
python3 new_service.py
```

You will be asked:

```
Project name (module name, e.g. github.com/me/orders): github.com/me/orders
Database name: ordersdb
```

- **Project name** becomes the Go module path (`go.mod`) and is used in every import. The directory name is the last path segment (`orders` in the example).
- **Database name** is written into `cmd/server/config.yaml` and the README.

The tool refuses to run if the target directory already exists, so it never overwrites existing work.

## Generated project structure

```
orders/
├── cmd/
│   └── server/
│       ├── main.go              # Server entry point and dependency wiring
│       └── config.yaml          # Server and database settings
│
├── internal/
│   ├── config/
│   │   └── config.go            # YAML config loader + DSN builder
│   ├── handler/
│   │   └── user_handler.go      # gRPC handlers
│   ├── service/
│   │   └── user_service.go      # Business logic and validation
│   ├── repository/
│   │   └── user_repo.go         # Database layer (pgx) + migration
│   └── model/
│       └── user.go              # Structs and domain errors
│
├── proto/
│   ├── user.proto               # Protobuf definitions
│   └── pb/                      # Generated by protoc (user.pb.go, user_grpc.pb.go)
│
├── go.mod
├── go.sum
└── README.md
```

`internal/config/` is an addition to the layout you described. It is needed so `main.go` can read `config.yaml`.

`proto/pb/` and `go.sum` only appear after `protoc` and `go mod tidy` succeed.

## How the layers are wired

Dependencies point inward, and each layer depends on an interface or the layer below it:

```
main.go
  │  loads config.yaml, opens the pgx pool, runs the migration
  ▼
handler.UserHandler        (gRPC <-> domain mapping, error codes)
  ▼
service.UserService        (validation, business rules)
  ▼
repository.UserRepository  (interface; implemented with pgx)
  ▼
PostgreSQL
```

The wiring in `main.go`:

```go
userRepo    := repository.NewUserRepository(db)
userSvc     := service.NewUserService(userRepo)
userHandler := handler.NewUserHandler(userSvc)

pb.RegisterUserServiceServer(srv, userHandler)
```

Because the service depends on the `UserRepository` interface, you can swap the implementation or mock it in unit tests without touching the service.

### Responsibilities

| Layer | File | Responsibility |
|-------|------|----------------|
| Model | `internal/model/user.go` | `User` struct and sentinel errors (`ErrNotFound`, `ErrInvalidInput`) |
| Repository | `internal/repository/user_repo.go` | SQL queries, `Migrate()` to create the table |
| Service | `internal/service/user_service.go` | Input validation, orchestration |
| Handler | `internal/handler/user_handler.go` | Converts proto <-> model, maps errors to gRPC status codes |
| Config | `internal/config/config.go` | Parses YAML and builds the Postgres DSN |
| Main | `cmd/server/main.go` | Startup, wiring, graceful shutdown |

## Configuration

`cmd/server/config.yaml`:

```yaml
server:
  port: 50051

database:
  host: localhost
  port: 5432
  user: postgres
  password: postgres
  name: ordersdb        # the name you entered
  sslmode: disable
```

The server reads `cmd/server/config.yaml` by default. Use the `-config` flag to point somewhere else:

```bash
go run ./cmd/server -config /path/to/config.yaml
```

The DSN is built as:

```
postgres://USER:PASSWORD@HOST:PORT/NAME?sslmode=MODE
```

> Do not commit real credentials. Keep production secrets out of `config.yaml`.

## gRPC API

Defined in `proto/user.proto` (package `user.v1`, service `UserService`):

| RPC | Request | Response |
|-----|---------|----------|
| `CreateUser` | `CreateUserRequest { name, email }` | `User` |
| `GetUser` | `GetUserRequest { id }` | `User` |
| `ListUsers` | `ListUsersRequest {}` | `ListUsersResponse { users[] }` |
| `UpdateUser` | `UpdateUserRequest { id, name, email }` | `User` |
| `DeleteUser` | `DeleteUserRequest { id }` | `DeleteUserResponse { success }` |

`User` message:

```protobuf
message User {
  int64  id         = 1;
  string name       = 2;
  string email      = 3;
  string created_at = 4;   // RFC 3339
}
```

The Go package for generated code is `<module>/proto/pb` (imported as `pb`).

### Database schema

Created automatically on startup by `repository.Migrate()`:

```sql
CREATE TABLE IF NOT EXISTS users (
    id         BIGSERIAL PRIMARY KEY,
    name       TEXT NOT NULL,
    email      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## Error handling

The service returns domain errors; the handler translates them into gRPC status codes:

| Domain error | gRPC code | When |
|--------------|-----------|------|
| `model.ErrNotFound` | `NotFound` | Get, Update, or Delete on a missing id |
| `model.ErrInvalidInput` | `InvalidArgument` | Empty name or email without `@` |
| anything else | `Internal` | Unexpected failures (details are not leaked to the client) |

Note: a duplicate email will currently surface as `Internal` because the unique-violation error is not mapped. See [Customizing](#customizing-the-generator) to add an `AlreadyExists` mapping.

## Running the generated service

```bash
cd orders

# If protoc was not available during generation:
protoc --go_out=. --go_opt=module=github.com/me/orders \
       --go-grpc_out=. --go-grpc_opt=module=github.com/me/orders \
       proto/user.proto
go mod tidy

# Start PostgreSQL and create the database (example with Docker)
docker run -d --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
docker exec pg createdb -U postgres ordersdb

# Run
go run ./cmd/server
```

Expected output:

```
gRPC server listening on :50051
```

The server shuts down gracefully on `Ctrl+C` or `SIGTERM`.

## Testing with grpcurl

Server reflection is enabled, so no `.proto` file is needed on the client side.

```bash
# List services
grpcurl -plaintext localhost:50051 list

# Create
grpcurl -plaintext -d '{"name":"Ali","email":"ali@example.com"}' \
  localhost:50051 user.v1.UserService/CreateUser

# Get
grpcurl -plaintext -d '{"id":1}' \
  localhost:50051 user.v1.UserService/GetUser

# List
grpcurl -plaintext localhost:50051 user.v1.UserService/ListUsers

# Update
grpcurl -plaintext -d '{"id":1,"name":"Ali H","email":"ali@example.com"}' \
  localhost:50051 user.v1.UserService/UpdateUser

# Delete
grpcurl -plaintext -d '{"id":1}' \
  localhost:50051 user.v1.UserService/DeleteUser
```

> Reflection is convenient in development. Consider disabling it in production.

## What the script does step by step

1. Prompts for the module name and database name (both required).
2. Derives the directory name from the last segment of the module path.
3. Exits if that directory already exists.
4. For each template in the `FILES` dictionary:
   - replaces `__MODULE__` and `__DB__`,
   - creates parent directories,
   - writes the file with UTF-8 encoding and LF line endings.
5. If `go` is not on `PATH`, stops and tells you to run the Go commands yourself.
6. Runs `go mod init <module>`.
7. If `protoc`, `protoc-gen-go`, and `protoc-gen-go-grpc` are all found, runs `protoc` to generate `proto/pb/`. Otherwise prints the install and run commands.
8. Runs `go mod tidy`. If it fails (usually because `proto/pb/` does not exist yet), prints a hint.

## Customizing the generator

All content lives in the `FILES` dictionary at the top of `new_service.py`. Each key is a relative output path and each value is the file template.

Placeholders available in every template:

| Placeholder | Replaced with |
|-------------|---------------|
| `__MODULE__` | The project/module name you entered |
| `__DB__` | The database name you entered |

Common changes:

- **Add a file**: add a new `FILES["path/to/file"] = r"""..."""` entry.
- **Change the default port or credentials**: edit the `config.yaml` template.
- **Use a different entity**: replace `user` / `User` across the proto, model, repository, service, and handler templates. A natural next step is to add a third prompt for the entity name and substitute it with another placeholder.
- **Map duplicate emails to `AlreadyExists`**: in the repository, detect `*pgconn.PgError` with code `23505`, return a new `model.ErrAlreadyExists`, and map it to `codes.AlreadyExists` in `toGRPCError`.
- **Switch database**: replace the pgx code in the repository and `DSN()` in the config template.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `Directory X already exists.` | Target folder present | Remove it or choose another name |
| `Go is not installed...` | `go` not on `PATH` | Install Go, then run `go mod init` and `go mod tidy` manually |
| `protoc or its plugins are not installed` | Missing tools | Install them (see [Requirements](#requirements)) and run the printed `protoc` command |
| `protoc-gen-go: program not found` | `GOPATH/bin` not on `PATH` | `export PATH="$PATH:$(go env GOPATH)/bin"` |
| `go mod tidy` fails with missing package `.../proto/pb` | Protobuf code not generated yet | Run `protoc`, then `go mod tidy` again |
| `db connect` / `db ping` error at startup | PostgreSQL not running or wrong credentials | Check `config.yaml` and that the database exists |
| `config: read config: ... no such file` | Running from the wrong directory | Run from the project root or pass `-config` |

## Limitations

- Generates a single entity (`user`) as a template.
- PostgreSQL only.
- Uses a startup `CREATE TABLE IF NOT EXISTS` instead of versioned migrations.
- No authentication, TLS, logging middleware, or tests are generated.
- Config values are read from YAML only (no environment variable overrides).
